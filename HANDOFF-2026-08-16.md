## 3. Committed but NOT deployed

**`survos-sites/imgproxy@3eb54fd`** — 39 non-secret values moved from `dokku config` into the
Dockerfile. Production still runs `f6027ec`.

⚠️ **Dokku config OVERRIDES image ENV.** Deploying without the matching `config:unset` changes
nothing — the old values silently keep winning. The full key list is in the Dockerfile comment.
Also needs:

```bash
dokku storage:unmount imgproxy /mnt/volume-1/imgproxy-presets.conf:/etc/imgproxy/presets.conf
```

The three presets (`thumb`/`display`/`archive`) previously existed **only** in that untracked file.
Deploy to the *current* host first and confirm images render, before the fsn1 relocation (#6) —
otherwise a wrong preset string and a new server fail at the same moment.

## 4. Backups

```
02:00  /root/.postgres.sh       → pg17 (localhost)      7.3 GB/night
02:30  /root/.postgres-pg18.sh  → pg18 legacy            719 MB, 11 dbs verified
03:00  /root/.postgres-new.sh   → pg.survos.com          653 MB, verified
```

**The gap that was closed:** the PG 18 cluster had *no backup at all*. `archive_mode=on` but
`archive_command='cd .'` — a Patroni placeholder that always exits 0, so `pg_stat_archiver`
reported 8,056 successful archives while discarding every WAL segment. `lingua`'s 3M translations
were unprotected.

**Still to do:** `/root/.postgres.sh` checks `$?` after `pg_dumpall | gzip`, which is *gzip's*
status. A failed dump logs "Backup successful" and leaves a useless file. This is not theoretical —
it happened on the new job's first run and was caught only because that script uses
`${PIPESTATUS[0]}`. One-line fix:

```bash
ssh root@5.161.107.103 'sed -i "s/if \[\[ \$? -eq 0 \]\]/if [[ \${PIPESTATUS[0]} -eq 0 \]\]/" /root/.postgres.sh'
```

All three are logical dumps, not PITR. **pgBackRest is the real fix** and already ships inside the
timescaledb-ha image — see #5.

## 5. Corrections — things that were checked and were wrong

These cost real time; recording them so they cost it once.

**DBAL 4 requires `serverVersion`.** Advice to drop it "so Doctrine auto-detects" is DBAL 3
behaviour. DBAL 4.4.3 removed auto-detection: omitting it fails with
`Invalid platform version "" specified`. Found by breaking lingua locally *after* the same change
had been staged into three apps' `CLAIMS_DATABASE_URL`. To decouple the version, set
`doctrine.dbal.server_version` per app in `doctrine.yaml`, not per-URL.

**`template1` propagates extensions.** The timescaledb-ha image ships `template1` with
`timescaledb` + `timescaledb_toolkit`, so every `CREATE DATABASE` inherits them. This hit the dev
box (33 databases, 0 hypertables) *and then the new production cluster*. It caused `pg_dump` to warn
that dumps might not restore without `--disable-triggers` — directly undermining the backup-based
purge policy. Dropped from `template1`, `postgres`, `lingua`, `mediary`; warnings gone.
`~/sites/docker/bin/drop-unused-timescaledb.sh` does the dev side and is **still unrun**.

**`.pgpass` matches the literal host string**, not the resolved IP. An entry keyed by IP does not
help a script that connects by hostname.

**Do not check `$?` after a pipe.** See §4.

**`dokku apps:destroy` prints "Unlinking from &lt;5 services&gt;" for every app** — it is a no-op loop
over all service instances, not evidence the app was linked.

**Not everything on dokku-ash is Dokku.** Cross-referencing directories against
`dokku storage:list` alone wrongly flagged the live PG 17 data directory and LibreTranslate as
orphans. Always also check `systemctl list-units --state=running`, `ss -tlnp`, and `docker ps`
mounts.
